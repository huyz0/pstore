# pstore and Vespa: architecture and feature comparison

**Snapshot:** 2026-10-29. **pstore:** `c7a0af5` (main after M159 and M180).
**Audience:** engineers deciding which Vespa ideas pstore should adopt, and which it must not.

Vespa and pstore answer the same question, "search over vectors, text and filters with
ranking", from opposite ends. Vespa keeps every searchable structure on the content node
that owns it, in memory or on local disk, and spends that locality on rich ranking: tensor
math, multi-phase rank profiles, in-engine model inference and a grouping language. pstore
keeps nothing on a node and makes the blob store the only durable tier, and spends that on
cost, tenancy scale, elasticity and snapshot semantics.

Neither is a subset of the other. Vespa is far ahead on **ranking expressiveness, result
shaping, partial updates and warm latency**. pstore is ahead on **storage cost, the number of
independent indexes it can hold, elasticity without data movement, and consistency
guarantees** (snapshot isolation, CAS fencing, time travel, branches). The recommendations at
the end take Vespa's ranking and result-shaping ideas and leave its storage and control-plane
design where it is.

This is a companion to the [turbopuffer comparison](turbopuffer-2026-10-25.md). turbopuffer
is a migration target, so that report audits wire compatibility field by field. Vespa is not a
migration target (its API, schema language and deployment model are its own), so this report
compares capability and architecture, and asks which ideas carry over.

## Evidence and interpretation

Vespa evidence is the public documentation at docs.vespa.ai, the Vespa blog and the Vespa
Cloud price calculator, read on 2026-10-29. Every row that depends on a specific Vespa
behaviour links the page it came from. Rows without a link describe long-standing, widely
documented Vespa features (the `weakAnd` and `wand` operators, the grouping language,
document references, predicate fields, embedders and ONNX ranking). They were not re-read
for this snapshot, so check the reference before acting on one.

pstore evidence is this repository: milestone specifications and verification records, the
research corpus, and the source at the commit above. The Rust suites were **not rerun** for
this documentation task, no Vespa instance was deployed, and nothing here is a measured
performance comparison. Labels in the tables are about capability, not wire compatibility:

| Label | Meaning |
|---|---|
| Vespa ahead | Vespa has it and pstore does not, or has a much narrower form |
| pstore ahead | pstore has it and Vespa does not, or only with a much weaker guarantee |
| Comparable | Both have the capability; mechanisms, defaults or limits differ |
| Different by design | The two systems chose opposite sides of a trade-off on purpose |

## The two architectures in one table

| Concern | Vespa | pstore |
|---|---|---|
| Durable tier | Each content node's local disk: a transaction log synced on every write, a document store and flushed index files ([proton](https://docs.vespa.ai/en/content/proton.html)) | The blob store only, for data and metadata ([architecture](../research/11-design/architecture.md)) |
| Who holds the data | Content nodes own buckets of documents. Redundancy sets the number of copies and `searchable-copies` how many are indexed ([sizing](https://docs.vespa.ai/en/performance/sizing-search.html)) | Nobody. Nodes own nothing; cache affinity is an optimisation, not a correctness requirement |
| Control plane | Config servers on ZooKeeper (3 for one failure) receive the application package and push config. A cluster controller with an elected master decides which content nodes are up ([config server](https://docs.vespa.ai/en/operations/configuration-server.html), [overview](https://learn.vespa.ai/what-is-vespa/architecture-overview)) | None. Membership is SWIM gossip seeded from the blob store, and a wrong view costs cache hits, never correctness ([membership](../research/04-cluster/membership.md)) |
| Commit and fencing | Per-document writes with wall-clock timestamps; replicas reconciled by a newest-timestamp-wins merge ([consistency](https://docs.vespa.ai/en/content/consistency)) | One CAS'd HEAD per tenant; a paused or partitioned writer is fenced by the storage layer ([manifest and CAS](../research/03-metadata-consistency/manifest-and-cas.md)) |
| Where queries run | A stateless Java container scatters to every content node in one group; each node matches and ranks its share, the container merges, then fetches summaries for the winners ([query API](https://docs.vespa.ai/en/querying/query-api.html)) | Any node: the query plan is three blob rounds to rank and one more to fetch rows ([query path](../research/08-query-engine/query-path.md)); a large index can be split across peers ([M54](../milestones/M54/SPEC.md)) |
| Vector index | HNSW, in memory, with raw vectors in memory unless `paged` ([HNSW](https://docs.vespa.ai/en/querying/approximate-nn-hnsw)) | Clustered (SPFresh/LIRE) lists with 1-bit RaBitQ codes and an int8 rerank; HNSW is rejected because its hop chain is data-dependent ([survey](../research/06-indexing/vector-index-survey.md)) |
| Hot data | Attributes, the memory index and the HNSW graph are memory-resident by design | A cache over immutable objects; cold is 30 to 60 times warm ([cold start](../research/07-caching/affinity-and-coldstart.md)) |
| Scaling out | Add nodes or groups live; buckets are redistributed with minimal movement and no re-feed ([sizing](https://docs.vespa.ai/en/performance/sizing-search.html)) | Add nodes; nothing moves, because nothing is owned. Elasticity is in seconds, bounded by cache warm-up |
| AZ or node loss | Coverage drops until copies are indexed elsewhere; stale reads are possible if every replica holding the newest version is down ([consistency](https://docs.vespa.ai/en/content/consistency)) | A cold-start event, not a data event: the blob store is the cross-AZ replica ([AZ topology](../research/04-cluster/az-topology.md)) |
| Unit of tenancy | A schema in an application package, deployed through the config servers. Many small tenants fit inside one schema via streaming mode groups | An index created through the API; about 50M indexes across 1M tenants is the design target, and an idle index costs only its stored bytes |
| Language | C++ content nodes (proton), Java containers and plugins | Rust, one binary for every role |

The table's middle rows decide most of the rest. A system with node-local, memory-resident
state can evaluate an arbitrary function over **every** match on a node, because reading a
field costs nanoseconds. A system whose next byte is 30 ms away cannot, so it ranks a
candidate window fetched in a bounded number of rounds. Vespa's ranking strength and
pstore's cost and tenancy strength are two consequences of the same choice.

## Storage and indexing

| Capability | Vespa | pstore | Assessment |
|---|---|---|---|
| Write durability at acknowledgement | "Written and synced to disk" on the replicas before the response ([consistency](https://docs.vespa.ai/en/content/consistency)) | `batched` by default (held in memory, flushed in a cross-index bundle); `durable` and `applied` on request ([M129](../milestones/M129/VERIFIED.md)) | Different by design. Vespa's default is the safer one; pstore's default is a cost choice that a caller must know about |
| Write visibility | Searchable within milliseconds after the response | About 1 ms through the replicated memtable; folded state through the HEAD | Comparable |
| Text index | Memory index flushed into disk indexes and fused; positions kept by default for proximity ranking ([proton](https://docs.vespa.ai/en/content/proton.html)) | Postings in immutable segments with exact term frequency, no positions ([text format](../../crates/pstore-format/src/text.rs)) | Vespa ahead on positional and proximity features |
| Filterable fields | `attribute` fields in memory, with `fast-search` dictionaries; required for grouping and sorting | Typed attributes in segments with zone maps; trigram sketches for patterns | Comparable capability; Vespa trades memory for latency, pstore bytes for cost |
| Vector precision | `double`, `float`, `bfloat16`, `int8`; binarise with `pack_bits` and search by `hamming`; full precision `paged` to disk for reranking ([binarising](https://docs.vespa.ai/en/rag/binarizing-vectors.html)) | f32 input; 1-bit RaBitQ codes with an int8 rerank in the same round ([quantization](../research/06-indexing/quantization.md)) | Comparable mechanism. Vespa exposes the precision as a schema type; pstore hides it inside the index (public f16/i8 types are workstream D) |
| Compaction | Document store compaction, disk index fusion, LID-space compaction; up to 2x temporary disk | Leveled compaction biased against read amplification, about ten segments per query ([compaction](../research/05-storage-engine/compaction.md)) | Different by design |
| History | Old versions removed by compaction; tombstones pruned after a TTL | Immutable segments give MVCC, `as_of` time travel and one-PUT branches ([MVCC](../research/05-storage-engine/mutations-and-mvcc.md)) | pstore ahead |
| Data left in the customer's files | None; documents are fed | Parquet and Lance columns indexed in place ([M69](../milestones/M69/SPEC.md), [M82](../milestones/M82/SPEC.md)) | pstore ahead |

## Vector search

| Capability | Vespa | pstore | Assessment |
|---|---|---|---|
| ANN algorithm | HNSW, `max-links-per-node` and `neighbors-to-explore-at-insert` per field; changing them needs a restart but no re-feed | Clustered lists, probe count per query, exact scan for small indexes | Different by design. HNSW is the lowest-latency choice in memory and the wrong one at 30 ms a hop |
| Recall knob | `targetHits`/`totalTargetHits` and `hnsw.exploreAdditionalHits`; `approximate:false` for exact | Probes, `exact`, opt-in exact rerank (`rerank: exact`, outside D-34's budget) | Comparable |
| Filtered ANN | Pre-filter by default, post-filter by `post-filter-threshold`, exact fallback below `approximate-threshold`, ACORN-1 style filter-first. `geoLocation` and `predicate` are not pre-filtered and can return fewer hits than asked ([HNSW](https://docs.vespa.ai/en/querying/approximate-nn-hnsw)) | Clustered lists compose with pre-filtering without islands or dead ends ([filtering](../research/06-indexing/filtering.md)) | pstore's structure suits selective filters; Vespa needs thresholds to avoid graph pathologies |
| Total hit counts under ANN | Not accurate, as with `weakAnd` | A count is a separate aggregation over the filter's rows ([M65](../milestones/M65/SPEC.md)) | pstore ahead on exact facet counts beside a ranked page |
| Multi-vector documents | Mixed tensor (map of vectors); a document is found by its closest vector; ColBERT-style MaxSim as a tensor ranking expression | Named multi-vector fields, exact MaxSim ([M61](../milestones/M61/SPEC.md)) and the MUVERA encoding ([M67](../milestones/M67/SPEC.md)) | Comparable families; Vespa's is general tensor math, pstore's is two fixed scorers |
| Sparse vectors | Mapped tensors and the `wand` operator over weighted sets | Library index only; public sparse search is workstream D | Vespa ahead |
| Distance metrics | `euclidean`, `angular`, `prenormalized-angular`, `dotproduct`, `hamming`, `geodegrees` | Dot product, cosine, squared Euclidean | Vespa ahead (notably `hamming` for binary embeddings) |
| Memory per billion vectors | Graph plus vectors in memory; the binarising guide shows the HNSW graph at about 6% of tensor bytes | 1-bit codes, about 96 GB per billion, served from cache over the blob store | pstore ahead on cost per stored vector |

## Ranking

This is the widest gap, and the one with the most to learn from.

| Capability | Vespa | pstore | Assessment |
|---|---|---|---|
| Where a ranking is defined | Named **rank profiles** in the schema, with inheritance, functions and declared query inputs; the query selects one with `ranking` | Inline per request: legs, a fusion, an optional boost | Vespa ahead: profiles are versioned with the schema, testable, and keep queries short |
| Expression language | Any arithmetic over scalars and tensors, `if`, decision trees, tensor `map`/`reduce`/`join` | Linear, saturating, decay and equality boosts over a window ([M62](../milestones/M62/SPEC.md)); exact scoring expressions are workstream E | Vespa ahead |
| Phases | `first-phase` over every match on a node; `second-phase` over the best 100 per node by default; `global-phase` in the container over the best 100 globally by default ([phased ranking](https://docs.vespa.ai/en/ranking/phased-ranking.html)) | The leg ranks; a boost or MMR rescores a window of at most 1,000 in the row round | Comparable shape for phases two and three; Vespa's first phase has no pstore equivalent because it needs every match's fields in memory |
| Fusion and normalisation | `reciprocal_rank`, `reciprocal_rank_fusion` (k defaults to 60) and `normalize_linear` in the global phase | RRF and `sum` across legs and an outer RRF over a multi-query ([M142](../milestones/M142/SPEC.md)) | Vespa ahead on normalisation functions |
| Model inference | ONNX models on content nodes or in the container (cross-encoders, learning to rank); built-in embedders at write and query time | None; workstream J is optional | Vespa ahead, by product choice |
| Feature export | `match-features` and `summary-features` return the values a ranking used, per hit | `$dist` on a dense leg and an optional fused `score` | Vespa ahead; this is what learning-to-rank and debugging need |
| Diversity and group quotas | Grouping with `max(n)` per group; diversity settings in match phase | MMR over a window ([M64](../milestones/M64/SPEC.md)); a hard per-group limit ([M146](../milestones/M146/SPEC.md)) | Comparable |

## Distribution and consistency

| Guarantee | Vespa | pstore | Assessment |
|---|---|---|---|
| Model | Eventually consistent, "a limited subset of AP"; reads best effort, not linearizable ([consistency](https://docs.vespa.ai/en/content/consistency)) | Snapshot isolation with eventual, session, bounded, strong and `as_of` reads ([consistency model](../research/03-metadata-consistency/consistency-model.md)) | pstore ahead |
| Search snapshot | Searches can briefly see a partial update; visitors have no snapshot isolation | Every leg, aggregation and facet of a request reads one snapshot ([M131](../milestones/M131/SPEC.md), [M164](../milestones/M164/SPEC.md)) | pstore ahead |
| Ordering | Wall-clock timestamps; NTP recommended, since drift can misorder writes | Epochs and CAS; no clock in correctness | pstore ahead |
| Failure modes | A node partitioned past the tombstone TTL can resurrect deleted documents, and Vespa does not detect it. A failed write can leave replicas divergent until merge | A fenced writer cannot publish; the work still needed is a pure function of the manifest ([ownership](../research/04-cluster/ownership-and-leases.md)) | pstore ahead |
| Coverage under failure | Results report coverage while copies are re-indexed; `searchable-copies` sets the recovery speed | No node holds the only copy of anything; a lost node is cache warmth | pstore ahead on durability, Vespa on predictable warm latency during the loss |
| Strong read cost | Not offered as a mode | One HEAD read, or zero with a session token ([session protocol](../research/11-design/session-and-affinity-protocol.md)) | pstore ahead |

## Multi-tenancy: streaming mode is Vespa's answer to pstore's question

Vespa's [streaming mode](https://blog.vespa.ai/scaling-personal-ai-assistants-with-streaming-mode/)
is the closest thing it has to pstore's tenancy model, and worth studying for that reason.
The tenant (the "group") is embedded in the document id, so one user's documents sit on a few
nodes and a contiguous region of disk. Nothing is indexed: a query must name its group and is
answered by an exact scan of that group's documents, vectors included. Data is "100% disk
based", writes are "several orders of magnitude" cheaper than with an index, and vector search
is exact. The blog quotes storage below $0.30 per GB-month on Vespa Cloud.

This is the same observation the pstore research made independently: most indexes are small,
and a small index should be scanned, not indexed ([survey](../research/06-indexing/vector-index-survey.md)).
The differences are where the bytes live and what crosses the boundary. A Vespa group still
lives on content nodes that own it, inside one schema deployed for every tenant; it cannot
have its own schema, and a group too large to scan has no index to fall back to. A pstore
index is its own API object with its own schema, scans when small and builds the clustered
index when large, and costs only blob bytes while idle. Streaming mode confirms the direction
rather than suggesting a change.

## Operations and cost

| Area | Vespa | pstore |
|---|---|---|
| Deployment unit | An application package (schemas, rank profiles, models, `services.xml`) deployed through config servers; most changes live, field type changes refused ([features](https://docs.vespa.ai/en/features.html)) | A binary with environment configuration; schemas belong to indexes created through the API |
| Schema evolution | Add fields and reindex in the background without re-feeding (the binarising guide's migration path) | `PATCH` schema refuses today; evolution is workstream G |
| Managed offering | Vespa Cloud, with autoscaling, zones and global endpoints | Self-hosted, BYOC; no managed service |
| Maturity | Years of production at Yahoo scale; open source since 2017 | Pre-production; every latency objective is `blocked` until cloud measurements exist ([SLOs](../research/11-design/slos.md)) |
| Price unit | Allocated resources. Commercial list price $0.145 per vCPU-hour, $0.0145 per GB of memory per hour and $0.0005 per GB of disk per hour, falling up to 50% with volume; enterprise has a $20,000 monthly minimum ([price calculator](https://cloud.vespa.ai/price-calculator)) | The customer's own cloud bill: blob bytes and requests, compute, cache disks ([cost model](../research/10-benchmarks-cost/cost-model.md)) |

Some arithmetic on the list prices, to size the gap rather than to claim a result. Vespa's
memory price is about $10.6 per GB-month and its disk price about $0.37, before volume
discounts. One billion 768-dimension `bfloat16` vectors are about 1.5 TB in memory, or about
$16,000 a month for memory alone at list price, before the HNSW graph, attributes, redundancy
and compute. Binarised, the same vectors are about 96 GB plus the graph, and full precision can
be `paged` to disk. pstore's research puts stored bytes at about $70 per TB-month in the blob
store and serves from a cache sized for traffic rather than corpus
([cost and latency](../research/02-object-storage/cost-and-latency.md),
[storage to cache ratio](../research/07-caching/storage-to-cache-ratio.md)). The honest
conclusion is the one the turbopuffer report reached: these are different units, no
comparative dollar or latency advantage is established, and a fair comparison needs equal
recall, durability, consistency and workload on the same cloud. What can be said is that
Vespa's costs scale with corpus bytes held hot, and pstore's with bytes queried; for a large
corpus that is mostly idle, that difference is the whole business case.

## Where each system is the better choice

**Choose Vespa** when ranking is the product: learning-to-rank, cross-encoders, tensor
features, business rules evaluated over every match, rich grouping, and a corpus whose hot set
is most of the corpus and must answer in single-digit to tens of milliseconds. It is also the
mature choice when a team can run a stateful cluster with a control plane, or buy Vespa Cloud.

**Choose pstore** when the shape is many independent indexes (millions of tenants, most of
them idle), when storage must cost blob prices, when an AZ loss must not be a data event,
when the deployment has to live in the customer's account with no control plane to operate,
or when results must be reproducible at a snapshot (`as_of`, branches, one snapshot per
request). Its cold queries are tens of times slower than warm ones, and it cannot run a model
or an arbitrary expression over every match; both are consequences of the design, not bugs.

## What pstore should not copy

| Vespa design | Why pstore keeps its own |
|---|---|
| HNSW as the primary index | Each hop is a dependent fetch; on 30 ms storage it breaks D-34's three-round budget ([survey](../research/06-indexing/vector-index-survey.md)) |
| Config servers on ZooKeeper and a cluster controller | A control plane is a master. pstore's premise is that blob CAS removed the need for one ([manifest and CAS](../research/03-metadata-consistency/manifest-and-cas.md)) |
| Buckets owned by content nodes and redistributed on resize | Ownership is what makes resizing a data-movement event; AGENTS.md forbids it |
| Wall-clock timestamps and newest-wins merge | Clock drift and tombstone resurrection are exactly the failure modes CAS fencing removes |
| A first phase evaluated over every match | Reading every match's fields is a scan of the index's attribute bytes; affordable in memory, not over the blob store. pstore ranks a bounded window instead, which is Vespa's second phase |
| Parent-child joins with global documents | A join is a data-dependent second fetch on the query path, and global documents copy data to every node. Denormalise at write time |
| Java plugin chains in the request path | Arbitrary user code on a shared, multi-tenant node is an isolation problem pstore does not need |

## Recommended pstore follow-ups

Each item names the workstream in the [delivery plan](turbopuffer-next-plan.md) it extends.
None claims a milestone number; each needs a specification with a checkable criterion before
work starts, following the [spec procedure](../../.agents/skills/spec/SKILL.md). Every item
must keep **0 LIST** and D-34's depth, and add no blob request that scales with records or
indexes. Ordered by value for effort, largest first.

| # | Follow-up | Vespa precedent | Workstream | Acceptance sketch |
|---|---|---|---|---|
| 1 | **A scoring expression language over the candidate window**: arithmetic, `if`, the existing boost functions as primitives, per-leg scores and BM25 per field as inputs | Ranking expressions, `second-phase` | E (exact scoring expressions) | A fixture set where the expression's ranking equals a reference evaluator's exactly; window and depth unchanged; the existing boosts expressible as expressions with identical output |
| 2 | **Per-hit feature export**: the leg scores, per-field BM25, `$dist` and the expression's inputs on each hit, on request | `match-features`, `summary-features` | E/H (computed signals, explain) | Features returned equal the values the ranker used, asserted by recomputing the final score from them |
| 3 | **Named rank profiles stored in the index schema**, with declared typed inputs, selected by name per query | Rank profiles, `inputs` | D/G (persistent schemas, evolution) | A query naming a profile ranks identically to the same expression sent inline; an undeclared input is refused at the door with no I/O |
| 4 | **Normalisation functions in fusion**: `normalize_linear` and `reciprocal_rank` with a constant beside RRF and `sum` | `global-phase` cross-hit functions | F | Golden fixtures for each function; a split query fuses identically to an unsplit one |
| 5 | **Expanded grouping**: nested groups, numeric buckets, min, max and avg, and hits per group | The grouping language | F (expanded grouping) | Fixtures checked against a reference over the same filter's rows at one snapshot |
| 6 | **Partial update operators**: arithmetic increment, add and remove on array attributes, resolved at fold | `increment`, collection `add`/`remove` | C | Concurrent increments from several writers sum exactly once each under applied completion; conditions see the pre-update row |
| 7 | **Dynamic pruning for BM25** (block-max WAND over the existing postings), measured before shipped | `weakAnd`, `wand` | E, performance | Identical top-k to exhaustive scoring on the judged set; bytes read per long query reduced by a stated, measured fraction; still global IDF |
| 8 | **Public sparse vectors with `hamming` beside the dense metrics** | Mapped tensors, `wand`, `hamming` | D | Exact results equal brute force; `hamming` over packed bits equal to a reference popcount |
| 9 | **Linguistics breadth**: an n-gram tokenizer for CJK and language detection as an opt-in analyser setting | OpenNLP and n-gram profiles | E (tokenizer versions, language) | Tokenizer output pinned by golden files and versioned in the schema, so an old segment never re-analyses differently |
| 10 | **Parallel bulk export by slices** with continuation tokens at one snapshot | Visiting with `slices` | H (export) | N slices together return each live row exactly once at the pinned epoch |
| 11 | **Stored query defaults** per index, such as a default profile, `top_k` or consistency | Query profiles | B | Defaults visible in the index summary; an explicit request field always wins |

Two Vespa capabilities are deliberately left for later. **In-engine model inference** (ONNX
rerankers and embedders) stays in optional workstream J: Vespa shows it is valuable, but it
puts GPU-or-CPU-heavy work on nodes sized for scans, and pstore's plan keeps model choice with
the owner. **Predicate fields** solve ad targeting, which is not a pstore workload today.

One Vespa lesson applies to the existing plan rather than adding to it. Vespa reports **search
coverage** when a node is down instead of silently returning fewer hits. When pstore splits a
query across peers ([M54](../milestones/M54/SPEC.md)) and a peer leg fails, the response
should say which segments answered. Check what the split path does today before specifying
anything; if it already falls back to local execution, the item is documentation only.
