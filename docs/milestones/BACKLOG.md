## Ordering, and why

Three principles, applied in this order:

1. **A criterion someone already wrote outranks a criterion nobody has written.** M0a's
   criterion 4 says "412, 409, 503 **and latency**" and the ledger says `NOT-RUN` for latency.
   That is a milestone reporting itself incomplete, and closing it costs less than arguing
   about what to do next.
2. **A cost that rises with time outranks one that does not.** Block-max pruning was the only
   item here that got *more* expensive every week: segments are immutable, so every segment
   written before the retrofit is permanently unprunable ([C-11](../research/06-indexing/full-text-search.md)).
   ⚠️ **Overturned by measurement** — [C-15](../research/06-indexing/full-text-search.md): the
   pruning skips zero bytes, so the rising cost was the cost of a *mistake*, and the principle
   ranked first the one item that should never have been built. The principle itself survives;
   what it needed was a number before it was applied, which is exactly what item 6b now has.
3. **A gate that measures less than it claims outranks the code it fails to measure.** If
   `scripts/coverage.sh` cannot see `pstore-engine`, every coverage number quoted about the
   correctness core has been meaningless, including this session's.

| 24 | ⚠️ **Nothing detects two servers writing one tenant on the same lane.** Lanes are single-writer and **dense**: a second process starts at `Seq::ZERO` and overwrites bundle 0, so acknowledged durable writes vanish with no error anywhere — a bundle is an unconditional `put`. `PSTORE_LANE` makes the lane an explicit operator choice and the server refuses to start without one, which turns a default into a decision; it does not turn a collision into an error. ⚠️ The fix is **create-if-absent bundles**, and it is not a one-line change: OQ-91's density invariant depends on a refused `PUT` **not** consuming the sequence number, so a `Lost` on a bundle write has to mean "another writer owns this lane" and fail the writer loudly, not retry into the next sequence. | [M7c](M7c/VERIFIED.md) | M |
| 26 | ⚠️ **A query is four sequential round trips and D-34 allows three.** The ranking is three — HEAD, the open round, the leg round — and the fourth carries the **ids**, because a payload's address cannot be known until the ranking exists ([M7c](M7c/VERIFIED.md) criterion 11, measured). It is flat in the segment count, which is the property that was at risk: review measured the first implementation at `3 + 2 × segments`, 19 rounds at eight segments. ⚠️ The way to three is a **format** change — ids read alongside the vectors a leg already fetches — which trades reading ids for every *candidate* against reading them for every *hit*, and is therefore a measurement rather than an opinion: at `top_k` 10 against a probed list of hundreds, the trade may not pay. | [M7c](M7c/VERIFIED.md) | M |
| 27 | ⚠️ **After a fold, no process knows an index's vector width without a read.** The write door refuses a batch whose width disagrees with the rows this process holds; once they are folded the width lives in the segment, and reading it would put a blob request on the write path. So a wrong-width write is accepted and the **next query** refuses — loud, but one step later than it should be, and the index now holds a segment nothing can query alongside its siblings. ⚠️ The fix is the same one M7d needs anyway: the width belongs in HEAD, as the first field of an actual schema. | [M7c](M7c/VERIFIED.md) | M |
| 25 | ⚠️ **The engine registry is unbounded**: one `Engine` per tenant, held for the life of the process, which is 1M of them at the scale the README claims. Eviction is not an LRU decision — an engine with unflushed rows holds **acknowledged writes**, so evicting one either discards them or must flush first, and that is a choice about what `batched` durability promises. Belongs with the schema questions, where there is a caller to ask. | [M7c](M7c/VERIFIED.md) | M |
